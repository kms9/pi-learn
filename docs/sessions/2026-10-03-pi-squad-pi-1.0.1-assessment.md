# 2026-10-03 Pi Squad 适配 Pi 1.0.1 的评估

## 用户要做什么

用户已更新 `pi-dev`，要求分析正在开发的 `pi_squad` 如何适配和优化。此次范围为源码、接口与现有设计评估；建议尚未实施，不作为新版功能验收结果。

## 达成了什么

**结论：保留薄 Extension + Go Controller 的架构，先补齐运行基线、工具暴露和输入边界，再优化收尾、请求证据及 UI。** 已使用的核心 Extension API 在目标源码中仍存在，没有发现必须重写 Controller 的接口删除。

本机 1.0.0 安装包的 `dist/core/extensions/types.d.ts` 存在，当前 doctor 要求的 14 个字符串均存在。这只说明声明扫描不会因这 14 项失败，不能证明运行行为或 1.0.1 兼容性。本轮未编译插件、未运行单元测试或三角色真实验收。

### 可沿用的接口

- `export default function (pi: ExtensionAPI)`、工具/命令注册和宿主提供的 `typebox`、`StringEnum` 仍适用；不需要改回旧 npm scope。
- `before_agent_start.systemPromptOptions.sections` 仍可组合修改。现有按进程固定 Role、按 Attempt 固定 working rules、按 Run 固定 Team 的装配方向正确。
- `agent_before_settle.outcome`、`agent_settled`、`ctx.isIdle()`、`ctx.hasPendingMessages()` 仍适用；现有 result_proposed 与真实 settled 分离的协议应保留。
- `session_before_switch/fork/tree`、`session_shutdown`、manual compaction、`user_bash`、UI prompt 和 autocomplete 接口仍存在。
- `createRead/Write/Edit/Grep/FindToolDefinition` 仍从 package 入口导出。现有文件工具继承原生 mutation queue，并在实际操作前复核 fence，继续保留。
- 0.87 已将模型上下文以 SessionManager projection 为准；现有生产入口没有直接改写 `agent.state.messages`，没有命中这项破坏性变化。

证据：`pi-dev/packages/coding-agent/src/index.ts`、`src/core/extensions/{types,runner,wrapper}.ts`、`src/core/agent-session.ts`，以及 `pi_squad/extension/{invocation,managed-files,team-roster}.ts`。

### 建议优先级

这里的 P0/P1/P2 是本轮适配建议的顺序，不是前序身份阶段的编号，也不是已确认需求。

| 优先级 | 工作 | 主要位置 | 完成判据 |
|---|---|---|---|
| P0 | 统一目标运行版与探针身份 | 安装环境、`USAGE.md`、`doctor.ts`、Controller doctor/probe | 实际 CLI、宿主导出 `VERSION`、安装类型、probe 与目标版一致；旧 probe 不冒充新版观察 |
| P0 | 明确状态工具暴露与 nested 权限 | `task-tools.ts`、`team-messaging.ts`、`execution-gate.ts`、`invocation.ts` | 协调/提交/yield/clarify 等工具不可被脚本嵌套调用；未授权 MCP、codemode、tool_search 与 nested 调用均受 gate 拒绝 |
| P0（启用 RPC 时） | 补 RPC 输入的受管分类 | `squad-commands.ts`、`invocation.ts` | Worker 的 RPC 输入不能混入正式工作；Leader RPC 输入按 guidance 处理或明确拒绝；不得静默放行 |
| P1 | 用工具结果结束正式 segment，明确串行状态操作 | `task-tools.ts`、`team-messaging.ts`、`invocation.ts` | 单个成功终结调用可结束自动 follow-up，仍等待真实 settled；混合工具 batch、错误和 pending 不被误判完成 |
| P1 | 修正有效 prompt/tools 的证据 | `context-assembly.ts`、`invocation.ts`、实际 probe | 能区分顶层工具、增量声明、有效集合及后置 hook；不能只靠全文 substring 或 `payload.tools` 宣称通过 |
| P1 | 降低能力检测对内部文件布局的依赖 | `doctor.ts`、`controller/project/{doctor,probe}.go` | 区分 unsupported、declarations unavailable、runtime unobserved；npm、managed、binary/source 各按真实支持范围处理 |
| P1 | 覆盖 fullscreen 与模式边界 | `dashboard.ts`、`team-roster.ts`、启动说明 | fullscreen/regular、窄 pane、resize、picker 取消及 dispose 行为正常；非 TUI 不调用 terminal-only custom UI |
| P2 | 查询结果 schema、工具元数据、精简 trace 与 renderer | 查询工具、`context-assembly.ts`、UI | structuredContent 有界且与 schema 一致；trace 可配置；元数据不被用作权限证明 |

### 1. 工具权限：active、callable 与 registered 已分开

0.99 新增 `ToolExposure`、`ctx.executeTool()`、`prepareLoadout()`。默认 `direct` 工具在 active 时既向模型声明，也可由另一个工具调用；`codemode/deferred` 工具即使不 active 也可能 callable。`model-only` 工具向模型声明，但不允许 nested 调用。

现有 Squad 工具没有显式 `exposure`，因此默认是 direct。建议将会改变执行状态的 `agent_invoke`、`agent_task_complete/yield/clarify/clarification_answer`、`squad_run_create/decide` 和正式 ask 的 `reply_message` 明确为 `model-only`。只读查询先维持 direct；若将来需要脚本组合查询，单独决定其边界。

**当前未证明存在工具绕过。** `Invocation` 的 `tool_call → gate.checkTool` 已做白名单，正式注入的 active 集合也未包含 codemode/tool_search。上游 `_executeNestedToolCall()` 会对 nested 调用执行同一 hook，并带 `parentToolCallId`。需要补的是这种保证在组合场景中的验证及事件关联，不能仅依赖 `setActiveTools()`。

在注入前检查所需工具的真实 exposure、来源和有效 active 集合。当前 `getAllTools()` 后按名称过滤只证明注册过；hidden 工具仍可能在 registry 中，却不能通过 active 集合启用。第三方同名覆盖和异步 MCP 工具注册也应进入兼容性观察。

正式任务继续采用现有 `read/grep/find/ls/write/edit` 受管边界。给 MCP 工具增加名称白名单不足以证明其操作遵守 write_set。只有形成独立的操作/副作用约束后，才考虑正式 Task 使用 MCP 或 codemode。

证据：`types.ts` 的 `ToolExposure`、`ToolDefinition`、`ToolCallEvent.parentToolCallId`；`agent-session.ts` 的 `_getCallableTools()`、`_executeNestedToolCall()`；`invocation.ts` 的 `tool_call` 与注入 loadout；`execution-gate.ts`。

### 2. RPC 输入：当前存在明确的静态覆盖缺口

`squad-commands.ts` 的 input handler 在 `event.source !== "interactive"` 时直接 continue；`Invocation` 只额外处理 `extension`。目标 Pi 的 RPC prompt/steer/follow_up 以 `source: "rpc"` 经过 input hooks。

因此，**如果允许受管 Squad 进程运行在 RPC 模式**，普通 RPC 输入目前不会执行 Worker interruption、Leader guidance 或 mention 分类。忙碌时的 steer/follow_up 可被 Pi 排队，影响同一正式执行上下文。这是源码能够定位的覆盖缺口，尚未进行真实复现。

建议将用户来源的分类覆盖 interactive/rpc；`@Role` 和图片的交互规则再明确选择支持或拒绝。若产品暂只支持 TUI，应明确阻止 RPC 正式激活，并在非 TUI 的 UI 入口返回可读诊断。不能把 RPC 当普通无关输入继续执行。

新版 RPC/SDK 的 `disposition` 可区分 handled/queued/started，但 **ExtensionAPI 的 `pi.sendUserMessage()` 仍返回 void**。现有 injection_requested → input_observed → result_proposed → settled 收据不能简化成读取 sendUserMessage 的返回值；也不能把 input_observed 当成 provider 已发送的证明。

证据：`pi_squad/extension/squad-commands.ts:632`、`invocation.ts:373`；`pi-dev/packages/coding-agent/src/modes/rpc/{rpc-mode,rpc-types}.ts`；`agent-session.ts` 的 `sendUserMessage()` 与 extension binding。

### 3. 收尾：用 terminate 减少对“请结束本轮”的依赖

当前 complete/yield/clarify/decide/reply 的成功结果主要在文本中要求模型结束。后续多一次 provider 请求可能增加耗时和 lease 压力，模型继续发工具也会遭 gate 拒绝。

建议这些真正结束 segment 的成功结果返回 `terminate: true`；将共享执行状态的工具声明 `executionMode: "sequential"`。`agent_invoke` 本身返回 child ID，仍需后续 yield，不能一律 terminate。工具失败也不能视为完成。

这属于可复用的既有优化：terminate 在旧版已经存在，并非 Pi 1.0 新 API。上游 `examples/extensions/structured-output.ts` 给出结构；`agent-loop.ts` 只在 **batch 中所有最终工具结果都 terminate** 时提前结束。因此串行也不意味着自动跳过 batch 中后续工具，混合 batch 必须验证，不能承诺一次字段添加就必然停止。

仍在 `agent_settled` 后检查 idle/no pending、outcome 和精确 binding/Attempt/segment，才向 Controller 认定完成。Pi 已将 settled handler 请求的新运行延后到所有 settled handlers 结束；现有 `setTimeout(0)` 又推迟一层，回调可能观察到随后开始的工作。建议收尾状态固定在当前 fence 下，并保留 native session change/manual compaction 的中断优先顺序；不要为简化代码直接删除所有延迟。

证据：`task-tools.ts`、`team-messaging.ts`；`pi-dev/packages/agent/src/agent-loop.ts` 的 `hasSequentialToolCall`、`shouldTerminateToolBatch`；`agent-session.ts` 的 `_emitAgentSettled()`；`invocation.ts` 的 delayed settle。

### 4. 请求证据：顶层 tools 与全文存在性不等于当前有效状态

`payloadEvidence()` 只从 `object.tools` 抽名称，以全文包含 Role/working/Team 字符串标记 present。1.0.1 的 Anthropic 适配器可保持初始顶层工具列表，将后续变化编码为消息里的 `tool_addition/tool_removal`，同名工具重新定义也在 inline block 中发生。部分其他适配器同样支持增量添加。

由此可静态确认：现在的 `tools` 记录可能只代表顶层字段，不能总称为当前有效权限集合；全文命中旧历史也不能证明当前有效 section。该问题影响证据可信度，不等同于 Controller 权限已经失效。

建议同时记录 task 期望集合、Pi 规范 transcript 的有效 tools/sections，以及 provider 特定的增量和最终有效集合。`@earendil-works/pi-ai` 已导出 `getCurrentTools()`、`getCurrentSystemMessage()`，可用于规范 transcript；它们不能直接用于任意 provider HTTP payload。

`before_provider_request` handlers 按加载顺序串行，后面的 handler 可以替换 payload。Squad 自己的 hook 只能证明它所见的请求阶段。最终验收仍需最后加载的观察扩展，并覆盖后置改写、自动重试、压缩、同名工具重定义；不要将只观察 parsed stream 的 `provider_stream_event` 当成最终请求证明。

生产 trace 可只保留必要 ID/hash/有界结构，完整逐请求探针由诊断配置启用。角色/Team 正文和控制凭据继续不落到 trace。context_edit 或压缩策略若后续采用，应保留原始审计历史和 refs；本次不引入自动清历史。

证据：`context-assembly.ts:payloadEvidence`；`pi-dev/packages/ai/src/api/anthropic-messages.ts` 的 `nativeToolChanges/convertMessages`；`src/utils/transcript.ts`；`coding-agent/src/core/extensions/runner.ts:emitBeforeProviderRequest`。

### 5. 能力、安装与 UI

TS/Go doctor 都扫描安装包内部 `dist/core/extensions/types.d.ts`。npm 安装本机路径可用，但声明存在不能证明 hook 顺序和边界行为，文件缺失也不能证明 API 不存在。`getPackageDir()` 在 native binary 指向 executable 目录，而 `copy-binary-assets` 没有复制该声明路径；依赖内部布局的检测会误拒绝这类安装。

建议记录 executable/package 路径、Pi VERSION、安装类型和 supported capability profile；声明扫描只作为可用的辅助证据，正式 ready 仍需与实际安装版本匹配的运行 probe。Controller `ReadProbe()` 已拒绝旧版号，值得保留。也要补当前依赖的 `session_compact_failed` 等声明与行为观察，而不只保留旧字符串清单。

`harness-hooks.mjs` 硬编码 `/usr/local/lib/node_modules/...`；只服务旧本地 harness，不能作为 managed/Nix/pnpm/binary 或目标源码的通用加载方法。现有 `npm test` 主要覆盖旧 config/messaging/inbox 模块，没有直接覆盖当前 `Invocation/team-extension`。通过旧测试不能宣称新版 Project runtime 已兼容；优先把这次适配补进既有真实集成矩阵，遵守当前不新增/运行单元测试的开发要求。

Pi 1.0 默认 fullscreen，可用 `--tui-mode regular`；1.0.1 的 `registerToolRenderer()` 能为尚未注册或恢复历史的工具提供 renderer。当前 Dashboard 使用原生 `ctx.ui.custom`，不需要重写 TUI。重点回归窄 pane、resize、关闭后的 timer/请求释放、补全取消、原生 picker 和 role 文件 mention 冲突。通过 `ctx.mode === "tui"` 保护 custom UI；hasUI 为 true 的 RPC 也不等于拥有完整 terminal UI。

0.99 后 `--no-extensions` 也禁用内置扩展，包括 llama.cpp provider；现有隔离启动命令仍适用，但不足以验证默认安装的 MCP/codemode 组合。使用该 provider 的检查须显式加载必要内置扩展。`/reload` 还会启用 defaultTools 中新增的工具，因此要验证 Squad 重新注册与受管 loadout 没有短暂放宽。

### 6. 后续优化与架构选择

只读查询可添加 `outputSchema + structuredContent`、准确 annotations，以及适量 namespace；保留 details 的状态用途，限制结构化结果大小，不能以 readOnlyHint 代替 gate。native renderer 与短 promptSnippet/guidelines 可改善面板阅读和工具使用。

Virtual Models 可提供按任务选择模型、成本/延迟观察，但路由会在每次请求运行且为实验性 API。若后续采用，应记录实际 physical model 与 routing policy、continuation/retry 行为，不静默改变已有 Role/Attempt 的规则。当前无需为升级强制加入模型路由。

`@earendil-works/pi-durable` 是另一套 experimental Harness/Conversation/Submission/Task API，README 明确 API 可跨版本改变。coding-agent 的 ExtensionAPI 未自动变成 Durable Extension。把现有运行迁入它需要另行比较持久化所有权、执行重放、副作用、用户会话及 Go Controller 的唯一调度权。本次建议先完成当前体系的兼容闭环，不把 Durable 的自动 resume 当作 Squad 失联自动恢复许可。

现有设计明确不承诺跨 Team 的历史隔离；新 context-edit API 不构成修改这一范围的授权。Role ownership、lease/fencing、独立验收、显式 recover/retry 和未知注入不自动重放等规则继续保留。

### 推荐实施与真实回归顺序

1. 选定实际 Pi 1.0.1 安装与 Node 基线；记录安装身份；安全空闲后再重启需要升级的进程，不混用旧 probe。
2. 补 model-only、状态工具串行/终结、RPC 模式与有效 loadout 检查，先跑一个 Worker 和一个 LeaderStep 的正式闭环。
3. 修正 prompt/tools 证据、doctor 安装判断；按实际支持的 providers 测当前上下文与工具集合。
4. 依仓库检查规则，关闭前次测试 space、新开独立 Herdr space，在当前 Project cwd 至少启动三个不同 Role Pi，并单独打开 Controller Dashboard；Team 场景增加 Leader。
5. 在既有阶段 04 场景中覆盖 direct → result_proposed → settled、capacity=1 的父子 yield、clarification、失租/取消、/new/reload/tree/manual compact、重复与迟到输入、后置扩展改写以及 MCP/nested 权限。
6. 再覆盖 fullscreen/regular、Picker/补全/preview 和 trace 成本。适配结果单独记录 Pi VERSION/固定 HEAD 与原结果的关系，未重测场景不继承新版 PASS。
