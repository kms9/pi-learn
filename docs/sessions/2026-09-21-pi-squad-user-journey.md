# 用用户历程审阅 Pi Squad 产品需求

## 用户要做什么

用实际使用过程理解当前产品需求，检查是否符合直觉。本页把现有需求转成用户可见行为，不新增需求或代表用户已认可本轮讲解。

## 当前产品定位

用户在一台Mac上手动运行多个Pi，让它们保持各自会话，通过对话发现、提问、委派和组成固定小队；可追踪结果，异常时由用户决定恢复。第一版执行成员均为Pi；前次Grok/Cursor参与设计评审，不等于产品已承诺直接纳管它们。当前是拟实现需求，尚未交付可运行产品。

## 用户历程

1. **第一次准备**：启动本地协作服务，为各Pi创建稳定身份并加载扩展；手动启动operator、worker、reviewer。仅主动加入同一实验空间的Pi互相发现，不扫描其他终端。身份跨正常重开保留，聊天历史是否恢复由用户决定。
2. **找到同伴**：在operator问“现在谁在线？各自在做什么？”。看到可联系状态、活动状态、工作目录等真实信息；在线不等于空闲。默认只列online，全部列表可查suspect/offline。不同目录可以互见，但发现不构成执行授权。
3. **联系同伴**：预设权限后可用自然语言发通知、提问或正式委派。通知只记录展示；提问在目标既有会话中进行受限只读回答，在线忙碌则排队；正式委派才有任务、状态、结果与验收。问答不隐式变成写文件任务。
4. **委派工作**：说“让reviewer读取numbers.txt并返回数量和总和”。先见任务已接受/排队，再看到执行状态与结果；目标沿用现有聊天，不自动新建会话。空闲执行，在线忙碌排队，同一Pi一项正式任务，不同Pi可以并行。执行结束与结果验收分别展示，模型说完成不是唯一证据。
5. **用户中途接管**：可去目标窗口输入或手动/new。明确关联的任务补充记录修订并继续；接管或普通插话使原attempt中断，向等待的上层反馈“未完成，用户已介入”，避免混合输出算成功；成功/new则旧任务中断，旧排队工作不会自动进入新聊天。取消排队不影响别的运行工作；取消运行须等中断证据，文件改动不自动回滚。
6. **固定小队**：用户事先配置leader、worker、reviewer等固定成员及权限，并亲自启动它们。在operator说“让小队完成统计、汇总和审查”。Leader拆解与交接，成员按依赖协作，审查失败最多返工2次。权限内不逐次确认；缺成员就阻塞，不自动启动或替换，成员恢复后用户显式resume。
7. **异常与恢复**：6秒无心跳suspect，10秒offline为实验目标；suspect/offline不接受新投递，不自动补发。恢复online后调用者重试。离线不释放身份，新Pi不能自动抢占；正常退出或用户显式释放后才能换实例。恢复服务只恢复记录与连接，执行结果未知的任务待核实，用户选择关联已有结果或创建新尝试。
8. **观察**：可查看名单、任务、阻塞与结果。最后可选Herdr位置跳转；没有Herdr也能协作。第一版不自动创建pane、搬运Pi或管理Agent进程。

## 审阅时特别留意的体验取舍

这些是现有规则的体验后果，供用户指出不合预期之处，不作为新增已决事项：

- 初次准备需要本地服务、身份与扩展，产品不代用户启动Pi。
- 第一版执行成员仅Pi，尚不包含原生Cursor/Grok/Codex runtime互调。
- 任务进入旧聊天，能使用原上下文，也可能受此前历史影响；干净聊天需要用户/new。
- 任务补充必须明确关联原任务；接管或普通插话会终结原attempt归属，并立即向上层反馈未完成。
- 失联后的可用性优先级低于身份占用保护；异常退出可能需要人工释放，恢复在线也不会自动补发失败工作。

## 阶段边界

00/01先交付“稳定身份＋在线发现”；02增加通知/问答，03增加正式任务，04增加固定小队，05增加可选Herdr观察。不应把后续完整用户历程当作00/01首版交付范围。

## 未决

用户已确认区分补充与接管，并要求介入时向上反馈未完成；其余历程仍可继续审阅。

## 历史澄清：“中途插话”为什么让任务待核实（被下文新决定细化）

适用范围是用户直接向**正在执行受委派正式任务的目标Pi**发送新的普通对话输入。用户在operator聊别的、打开观察界面或用只读命令查询任务状态，不等于向目标模型插入新指令。

例如operator委派reviewer统计numbers.txt，用户随后到reviewer说“先别统计了，检查README”。之后reviewer输出“完成”，系统不能继续认定统计任务已成功。现有阶段03合同保留原任务与证据、标needs_review/manual_interference，停止自动报原任务成功。这个标记本身不等于已中止Pi、任务失败、输出丢弃或文件回滚；实际取消另有流程。

严格之处在于当前普通输入没有区分“补充原任务”与“换一个任务”。因此直接在目标聊天里说“仍然统计，不过忽略空行”，甚至普通对话式“做到哪了”，也可能进入这条保守规则。查询任务命令与把问题发给模型不同。

解释中的可改进方向是：提供与原任务明确关联的补充入口，更新任务要求并记录；另设明确接管入口处理改目标。此为体验建议，未获用户选择，不是已确认需求，本轮不改阶段03合同。


## 用户确认：补充继续，介入向上反馈未完成

用户接受前述建议，并明确增加：上层节点正在监听/等待时，用户手动介入任务，应直接反馈“任务未完成，用户介入了任务”。本节取代上文“仅建议、未确认”和统一needs_review的旧描述。

例：A派B统计并等待。用户经任务补充入口告诉B“忽略空行”，记录到同一任务并继续；用户接管B说“先改README”，B原attempt标interrupted/manual_interference，A收到“统计任务未完成：用户已介入”，不再等统计成功，也不会自动换人重做。B后续改README的“完成”不能算统计完成。

通知是任务事实，不宣称Pi已停。父Pi忙/离线时仍先持久记录并更新可见状态，待能安全接收时报告；不抢占上层用户工作、不因恢复连接重新派发。依赖该任务的更上层节点也须得到明确阻塞原因。已运行且无依赖的其他工作不因反馈自动被取消。
