# 2026-10-09 Pi Squad 升级到 Pi 1.1.0 的影响评估

## 用户要做什么

先评估 Pi 1.1.0 对当前 Pi Squad 的影响，判断能否直接升级、需要哪些兼容调整，再决定升级实施。

## 达成了什么

**结论：源码与公共类型检查支持继续升级，预计只需局部适配，不需要重写 Go Controller；不能只修改版本常量后直接宣布兼容。** 升级前优先处理宿主 profile、取消后的收尾，以及本机 managed launcher 的安装身份匹配。工具权限、请求证据、原生操作和 TUI 需要真实回归。

本机默认 Pi 已安装为 1.1.0，因此后续工作是升级 Squad 的适配与支持范围。本次只分析与编译，未修改产品代码、安装环境、规格或上游 submodule，也未运行模型或三角色功能验收。以下优化是建议，尚未实施。

### 固定证据与检查范围

| 对象 | 本次核对 |
|---|---|
| Pi 1.0.1 基线 | 本地 `pi-dev` 的 release commit `a7229ddc21810d6245105978033b7df645ecc2f7`；通过 `git archive` 提取到临时目录 |
| Pi 1.1.0 目标 | 官方 `v1.1.0`，release commit `abe508e1b89912adde45528136c3221eb69acdd7`；官方 tag tarball 在仓库外临时解包 |
| 本地 submodule | 仍为 `4c6fb7cfe8c538a668726f6f8b3554098c39faee`，package 1.0.1；未更新工作区或 gitlink |
| Squad 代码 | overlay HEAD `c0214d5938fa5d16c3db36b41e9a66a00dae8ec8`；保留原有工作区文档改动 |
| 实际安装 | `/Users/logo/.local/bin/pi` 输出 1.1.0；managed release 内 coding-agent、pi-ai、agent-core、tui 均为 1.1.0 |
| 编译基线 | Node `v24.16.0`；TypeScript `7.0.2`；临时 tsconfig 对接实际 1.1.0 安装的公共声明 |

已完成的检查：

- 当前 `pi_squad/extension/**/*.ts`（排除测试文件）和兼容 observer `pi-probe.ts`，对 Pi 1.1.0 公共声明的严格 `tsc --noEmit` 检查通过。
- 当前 Go Controller 构建通过。临时二进制执行两次只读 `doctor`，没有启动 serve、模型或修改 Project runtime。
- 实际 1.1.0 的 types 声明中，doctor 要求的 18 项名称全部存在；这只是静态声明诊断。
- 无新的单元测试或真实功能验收。类型检查、构建和 doctor 均不能替代 1.1.0 的真实兼容结论。

### 1. 可以沿用的部分

对比固定 1.0.1 与 1.1.0 源码，Extension runner/wrapper、SessionManager 和 pi-ai transcript helpers 未变化。Squad 使用的 `systemPromptOptions.sections`、`context_with_system`、`before_provider_request`、session 切换/压缩与 UI hooks 仍保留。

`model-only`、`executionMode: sequential`、nested `parentToolCallId` 仍可沿用。agent loop 的差异主要增加工具计时，`terminate` 的 batch 判断没有变化，仍要求 batch 中所有最终结果都 terminate；不能把单个完成工具看作无条件跳过后续工具。

原生 write/edit 和 `file-mutation-queue.ts` 未变化，受管文件工具无需重写。read 新增 output schema/structuredContent，现有 [managed-files](../../pi_squad/extension/managed-files.ts) 通过展开原生定义和结果保留这些字段，暂未发现强制迁移点。

Go 控制面的 Team/Task/Attempt、租约、CAS、HTTP/SSE 与数据库不是此次上游 API 变更对象；当前没有证据要求更改这些协议或数据库 schema。

### 2. 升级前必须处理的项目

| 优先级 | 项目 | 当前影响 | 建议 |
|---|---|---|---|
| P0 | 宿主 profile | TS/Go doctor 和 probe 精确限定 1.0.1，当前 1.1.0 注册前被拒绝 | 将 Extension/Controller/observer/规格/使用说明同步到明确的 1.1.0 profile；继续拒绝未验证版本，不采用宽泛版本下界 |
| P0 | 取消后的收尾 | `agent_settled.aborted` 是 1.1.0 新的直接取消证据，Squad 当前忽略该事件内容 | aborted=true 优先于缓存的 completed；probe 记录该标记，成功生命周期明确要求未取消 |
| P0 | managed 安装身份 | 默认 CLI 是 shell launcher，Go doctor 的路径/hash 与运行时实际 CLI entry 不同 | 支持解析选定 managed release 的实际入口，或先统一通过具体 release 的 `node_modules/.bin/pi` 启动和诊断；不能取消安装身份验证 |

#### 取消路径的具体风险

Squad 的 [Invocation](../../pi_squad/extension/invocation.ts) 在 `before_agent_start` 将 outcome 置为 `completed`，只在 `agent_before_settle` 更新它；`agent_settled` 的参数名为 `_event`，未读取新 `aborted` 字段。

Pi 1.1.0 的 `AgentSession._runAgentPrompt()` 在 `_agentRunAbortRequested` 为 true 时跳过 before-settle boundary，但 finally 仍调用 `_emitAgentSettled()`，并发送 aborted=true。因此存在当前缓存仍为 completed、真实运行已经取消的静态路径；已经 result_proposed 后的取消尤其需要验证。Controller 当前按 [AttemptEvent 的 outcome](../../pi_squad/controller/scheduler/execution.go) 区分正常完成和 interrupted，因此可沿用现有协议传递取消语义。

建议在当前 fence 下使用 `event.aborted ? "aborted" : this.outcome` 等明确分类，保留 existing binding/session/generation、idle/no-pending 和 native compaction 的保护。[observer](../../pi_squad_case/04-team-orchestration/compatibility/pi-probe.ts) 与 [Go probe reader](../../pi_squad/controller/project/probe.go) 同步记录和校验取消信息；缺失该字段不能被当作 1.1.0 的成功证据。这是静态风险分析，尚未通过真实 Esc 复现，不应写为已发生的生产错误。

#### managed launcher 的具体诊断结果

| `--pi-binary` | doctor 识别的安装与入口 | 当前结果 |
|---|---|---|
| `/Users/logo/.local/bin/pi` | executable；`/Users/logo/.pi/agent/bin/pi`（shell launcher） | 1.1.0 被版本门拒绝，额外警告 package metadata unavailable，声明计数 0 |
| `/Users/logo/.pi/agent/install/releases/1.1.0/node_modules/.bin/pi` | npm；实际 `dist/bundle/cli.js` | 1.1.0 被版本门拒绝，无警告，声明计数 18 |

Extension `hostIdentity()` 哈希运行时 JS 入口；Controller `InspectCapabilitiesFor()` 只解 symlink 并哈希传入文件；`ReadProbeForHost()` 要求两侧路径/hash 完全匹配。即使改了版本门，默认 launcher 仍不能满足这项匹配。此问题属于安装布局变化，不能归因于 Extension API 删除。两次 doctor 没有真实 probe，`formal_execution_ready` 均为 false。

### 3. 需要回归、尚无证据要求重写的项目

| 累积变化 | 对 Squad 的影响与判断 |
|---|---|
| 1.0.4 的工具通配符和 MCP 保留规则，1.1.0 的 `+name/-name` | `--tools` 不再总能等同于只注册名单里的工具。生产 Task 仍由 `activateTaskTools()` 的精确 active 集合和 `ExecutionGate.checkTool()` 拦截；现有 model-only/nested gate 保留。没有证明出现权限绕过，但需要覆盖默认扩展、MCP 异步注册、codemode、tool_search、`--tools` 和 reload 的组合。基础启动继续按已有 `--no-extensions -e ...` 隔离方式，不用新修饰语替代 Squad 权限。 |
| 1.0.4 的 hidden loadout prompt 修正 | 系统 rules/skills 会按隐藏声明调整，新增 `getPromptGuidelines()`；Squad 自有 sections 的构造仍可用。canonical 期望集合、active 集合和末位 provider request 必须重新对齐。 |
| 1.1.0 的 `durationMs`、renderer `outputPad` | 增量字段；当前 Squad 不自行构造 tool render context，无强制迁移点。受管 read 继承原生新结果，nested 计时新增不改变既有权限 hook。 |
| provider 重试和 token 估算 | `server_busy` 等更多错误可重试，输出 token 预算按更保守估算处理。收尾仍应发生在 retry/compaction 真正结束后，验证取消重试与超限压缩；不是每次 agent_end 都可完成 Task。 |
| 1.1.0 的 OSC 7501 程序状态 | 对支持协议的终端提供进程状态，可改善 pane 观察；不能替代 Controller 的 Task/Run、验收或 stopped 收据。Herdr 实际显示、窄 pane、resize 和 picker 取消尚未验收。 |
| 1.0.3 的 Azure provider 重命名 | 只有使用旧 Azure provider 的配置需要迁移；其 Responses API ID `azure-openai-responses` 未改，不能删除 request-evidence 的该 API 分支。此前真实基线 `local-grok/grok-4.7` 不属于 Azure；本轮不读取或改用户凭据配置。 |
| 1.1.0 的 stream 类型收紧 | 自定义 stream 需返回 `AssistantMessageEventStream`。当前 Squad 未注册自定义 provider/stream，不命中此破坏性变化；不需要改 HTTP/SSE 消息解析器。 |

### 4. 推荐的升级顺序与完成判据

1. 在单独升级改动中明确目标为 Pi 1.1.0/TUI；保留精确版本检查。需要回退时准备独立 1.0.1 安装，不假设 managed installer 一定保留它；本机当前 release 目录只看到 1.1.0。
2. 实施上述三个 P0 项，同步宿主规格、USAGE/README 和兼容 observer。实际入口/profile/version/hash 必须一致；旧 1.0.1 probe 继续拒绝。
3. 按仓库规范关闭上一轮测试 space，建立新的可见 Herdr workspace，在项目 cwd 至少启动三个不同 Role、独立 Controller 和对应 Dashboard；验证正式完成、result_proposed 后 Esc、取消重试、child yield/clarify/answer、人工插话和 /new、/reload、compact/fork/tree、工具集合与末位请求证据。收尾资源归零才关闭测试 space。
4. 重新采集 1.1.0 真实 probe 与兼容结果；阶段 04 的正式升级结论应再跑既有 89 项矩阵，而不是复制 1.0.1 的 PASS。需要新增取消和 managed 诊断覆盖，额外 provider/native binary 仍按实际覆盖单独记录。

不建议在放开版本门后立刻切换所有正在执行的 Role。完成验证、现有任务安全空闲或明确收尾后，再统一重启所需进程并切换；本次没有停止用户服务。

此前决定的取消业务 120 秒硬截止、必要子任务未回传时禁止上层完成、Leader 当前上下文优化，是独立的 Squad 业务问题，Pi 1.1.0 不会自动实现。此次 provider 重试变化可能增加旧硬截止的干扰，建议分别记录影响，避免把这些尚未实施的优化算作上游已修复。
