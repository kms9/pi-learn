# 任务补充与用户介入向上反馈

## 决策

1. 明确关联原任务的补充，记录修订并继续原任务；不扩大权限。补充已应用的版本与完成结果必须对应。
2. 接管/改变目标，或向目标Pi提交未关联为任务补充的普通输入，标记原attempt为interrupted/manual_interference。
3. 上层监听/等待节点直接收到“原任务未完成，用户已介入”，结束等成功结果的状态；不让其无限等候，不把介入当成功或自动重试。

## 背景

先前规则只把原任务标needs_review，既未区分补充与接管，也未明确父节点怎样停止等待。用户接受区分两类输入，并要求介入立即向上反馈。

## 证据

用户：“嗯 按你的建议来 如果上层节点在监听/等待任务完成 但是过程中用户手动介入了任务 则上层直接反馈任务未完成 用户介入了任务等”。

## 影响

- 原attempt归属终结，不等于底层Pi已停；不能因此立刻把另一正式任务注入仍忙的Pi。
- 事件、状态与通知持久提交，去重；父依赖转needs_review/dependency_interrupted并沿等待关系传播原因，受影响下游不继续。
- 父Pi忙时先更新可见记录，空闲时安全报告；离线时保留状态通知，不谎称模型已回应，也不自动补派工作。
- 旧attempt晚到结果只入历史；重新关联证据、重试或改派由用户明确决定。
- 小队Leader收到相同反馈；不把介入当审查失败而自动返工。
- 查询任务状态不属于介入。补充通过明确入口关联task/attempt，不能只让模型猜自然语言意图。

## 复审触发条件

用户希望普通自然语言自动区分补充/接管，或要求自动重新规划与重派时重新确认；当前不隐式加入这些行为。
